## 0. บทสรุปผู้บริหาร

ตรวจแล้วพบว่า **ปัญหาหลักไม่ใช่เรื่องดีไซน์ แต่เป็นเรื่องสถาปัตยกรรมการเรนเดอร์**

หลักฐานที่วัดได้จริง (เสิร์ฟไฟล์จริงแล้ว `curl` ดู HTML ดิบ):

```
bytes ที่ส่งกลับ:              6,824
คำที่มองเห็นได้ใน <body>:      0
"จารุวัฒน์" ใน body:           0 ครั้ง (มีแค่ใน <title> กับ meta)
```

**เนื้อหาทั้งหน้าเป็นศูนย์สำหรับทุก crawler ที่ไม่รัน JavaScript** เพราะ `assets/js/app.js` โหลดทุก section ด้วย `fetch().innerHTML`

เรื่องนี้สำคัญมากกับโจทย์ที่ตั้งไว้ เพราะ:

| ตัวอ่าน | รัน JS ไหม | เห็นอะไร |
|---|---|---|
| Googlebot | รัน (แต่ delay เป็นวัน) | เห็นครบ — ช้า |
| GPTBot / OAI-SearchBot (ChatGPT) | **ไม่รัน** | หน้าเปล่า |
| ClaudeBot (Claude) | **ไม่รัน** | หน้าเปล่า |
| PerplexityBot | **ไม่รัน** | หน้าเปล่า |
| ATS / บอทดูดโปรไฟล์ของ HR | **ไม่รัน** | หน้าเปล่า |
| LINE / Facebook / LinkedIn preview | **ไม่รัน** | ไม่มีรูป ไม่มีคำอธิบาย |

> **ข้อสรุป: ต่อให้ออกแบบ UI ใหม่สวยแค่ไหน ถ้ายังฉีดเนื้อหาด้วย JS อยู่ โจทย์ "ให้ AI มาหาตำแหน่งเจอ" จะทำไม่ได้เลย**
> ดังนั้นงานข้อ 1 (สถาปัตยกรรม) ต้องมาก่อนงานดีไซน์ทั้งหมด

## 1. ทางเลือกที่ 1 — สถาปัตยกรรมการเรนเดอร์ (ต้องเลือกก่อน)

### แนวทาง A — รวมเป็น `index.html` ไฟล์เดียวแบบ static

เอาเนื้อหาจาก component ทั้ง 13 ไฟล์มาแปะใน `index.html` ตรงๆ ครั้งเดียวจบ

| ข้อดี | ข้อเสีย |
|---|---|
| ไม่ต้องมี build tool อะไรเลย | ไฟล์เดียว ~1,400 บรรทัด แก้ยากขึ้น |
| crawler เห็นครบทันที 100% | เสียการแยก component ที่ทำไว้ดีแล้ว |
| เร็วที่สุด — ยิงไฟล์เดียว ไม่มี 13 request | |
| GitHub Pages รองรับตรงๆ | |

### แนวทาง B — build step เล็กๆ ⭐ **แนะนำ**

เขียนสคริปต์สั้นๆ (Node หรือ shell ~40 บรรทัด) ที่เอา `component/**` มาต่อกันเป็น `index.html` ตอน build

```
component/  ──(build.js)──►  index.html   (static, commit ลง repo)
     ▲                            │
   แก้ตรงนี้                 GitHub Pages เสิร์ฟตัวนี้
```

| ข้อดี | ข้อเสีย |
|---|---|
| ยังแก้เป็น component เหมือนเดิม | ต้องจำว่าแก้แล้วต้อง build |
| output เป็น static 100% — crawler เห็นครบ | เพิ่มไฟล์ build script 1 ไฟล์ |
| ทำ 2 ภาษา (TH/EN) จาก source เดียวได้ | |
| ใส่ GitHub Action ให้ build อัตโนมัติตอน push ได้ | |

**หมายเหตุสำคัญ:** repo นี้คือ `darkneed02.github.io` = GitHub Pages
GitHub Pages **ไม่ build ให้** ดังนั้น `index.html` ที่ build แล้วต้อง commit ลง repo
(หรือใช้ GitHub Action build ให้ตอน push — แนะนำทำในเฟส 2)

และ `docker-compose.yml` mount root แบบ `:ro` ดังนั้น output ต้องออกที่ root ของ repo เท่านั้น

### แนวทาง C — ย้ายไป SSR framework (Astro / Next.js) ❌ **ไม่แนะนำ**

ตอบโจทย์ SEO ได้ดีที่สุดในทางทฤษฎี แต่:
- ขัดกับที่กำหนดไว้ว่า **"ใช้ css js ของธีมที่มีอยู่"**
- ธีมนี้พึ่ง jQuery + GSAP + WOW + Isotope + Swiper ซึ่งพังง่ายมากบน React lifecycle
- งานที่ควรใช้ 2 สัปดาห์ จะกลายเป็น 2 เดือน

**→ เลือก B**

## 2. ทางเลือกที่ 2 — สองภาษากับ SEO

ตอนนี้ EN มีอยู่แค่ใน `i18n.js` (สลับด้วย JS) แปลว่า **เวอร์ชันอังกฤษไม่มีตัวตนใน Google เลย** และไม่มี `hreflang`

สำคัญมาก เพราะ recruiter ต่างชาติ / บริษัท international / AI ที่ค้นเป็นภาษาอังกฤษ จะหาไม่เจอ

| ทางเลือก | ผลลัพธ์ |
|---|---|
| **B1 — สองหน้า static: `/` (ไทย) + `/en/` (อังกฤษ)** ⭐ | ทั้งสองภาษาถูก index จริง, ใส่ `hreflang` + `canonical` ไขว้กันได้, AI ค้นภาษาอังกฤษเจอ |
| B2 — ไทยอย่างเดียวเป็นหลัก EN เป็นแค่ปุ่มสลับ | ทำง่ายกว่า แต่เสียตลาด recruiter ต่างชาติทั้งหมด |

**→ แนะนำ B1** — ถ้าเลือกแนวทาง B (build step) ตัวสคริปต์สร้างสองหน้านี้จาก source เดียวกันได้เลย ไม่ต้องเขียนเนื้อหาซ้ำ

## 4. งาน SEO เฉพาะทางสำหรับ HR และ AI

ตอนนี้ **ไม่มีไฟล์เหล่านี้เลยสักไฟล์**: `robots.txt`, `sitemap.xml`, `llms.txt`, `resume.json`, OG tags, JSON-LD

### 4.1 ให้ AI crawler เข้าถึงได้ — `robots.txt`

ระบุอนุญาต bot ที่เกี่ยวกับการหางานให้ชัด: `GPTBot`, `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`, `PerplexityBot`, `Google-Extended`, `Bingbot` + บรรทัด `Sitemap:`

ถ้าบล็อกบอทพวกนี้ = แพลตฟอร์มนั้นอ้างอิงเราไม่ได้เลย

### 4.2 JSON-LD — `ProfilePage` ครอบ `Person`

ตัวนี้คือหัวใจของ "ให้ AI รู้ว่าเราคือใครและหางานตำแหน่งอะไร"

| field | ใส่อะไร |
|---|---|
| `name` / `alternateName` | จารุวัฒน์ อำนวยสัตย์ / Jaruwat Amnuaysat |
| `jobTitle` | Full Stack Developer, Programmer |
| `knowsAbout` | Golang, PHP, Vue.js, PostgreSQL, REST API, Docker, Automation |
| `hasOccupation` → `Occupation` | ชื่อตำแหน่งที่ต้องการ + `occupationLocation` |
| `worksFor` / `alumniOf` | บริษัทและสถาบัน (มีข้อมูลครบใน experience แล้ว) |
| `sameAs` | LinkedIn, GitHub, Facebook |
| `address` | **ระดับจังหวัดเท่านั้น** — "ปทุมธานี, ประเทศไทย" |
| `email` | อีเมลติดต่อ |

*(`Person.seeks` → `Demand` มีใน schema.org จริง แต่แทบไม่มีตัวไหนอ่าน — ใส่ได้แต่ไม่ต้องพึ่ง)*

### 4.3 `llms.txt` — สรุป CV แบบ markdown ล้วน

ไฟล์ text ที่ AI อ่านง่ายที่สุด วางที่ root: ชื่อ, ตำแหน่งที่หา, stack, สรุปประสบการณ์แต่ละที่, ช่องทางติดต่อ

### 4.4 `resume.json` — มาตรฐาน JSON Resume

มาตรฐานจริงที่เครื่องมือ AI matching / ATS หลายตัว parse ได้ตรงๆ ต้นทุนต่ำ ผลตอบแทนสูงสำหรับโจทย์นี้โดยเฉพาะ

### 4.5 คำในหัวเรื่องต้องตรงกับที่คนค้นจริง

ตอนนี้ `<title>` คือ *"จารุวัฒน์ อำนวยสัตย์ — Programmer & Developer"* — ค้นด้วยชื่อถึงจะเจอ แต่ **ไม่มีใครค้นชื่อคนที่ยังไม่รู้จัก**

ต้องมีคำที่ HR/AI ค้นจริง: ตำแหน่ง + stack + จังหวัด
เช่น `"Full Stack Developer (Golang/PHP/Vue) ปทุมธานี — จารุวัฒน์ อำนวยสัตย์"`

### 4.6 บล็อก FAQ + `FAQPage` schema

AI ดึงคำตอบเป็น "ท่อน" ไม่ใช่ทั้งหน้า — เขียนคำถามที่ HR ถามจริง คำตอบละ 40–60 คำ จบในตัว:
- "รับงานประเภทไหน / พร้อมเริ่มงานเมื่อไหร่"
- "ถนัด tech stack อะไรบ้าง"
- "ทำงาน remote / onsite ที่ไหนได้"
- "มีประสบการณ์กี่ปี ทำอะไรมาบ้าง"

### 4.7 เขียนผลงานเป็น "ตัวเลข"

งานวิจัย GEO (Princeton, KDD 2024) วัดผลกับ AI search engine พบว่า **การใส่สถิติ/ตัวเลขเพิ่มโอกาสถูกอ้างอิง ~37–40%** ส่วน **keyword stuffing ลดลง 10%**

แปลว่า: `"ลดเวลาประมวลผลรายงานจาก 4 ชม. เหลือ 12 นาที"` ทรงพลังกว่า `"พัฒนาระบบรายงาน"` มาก

### 4.8 Semantic HTML — เพราะ AI agent อ่าน accessibility tree

AI agent รุ่นใหม่อ่านหน้าเว็บผ่าน accessibility tree เดียวกับที่ screen reader ใช้
ดังนั้น `<main>`, `<article>`, `<section>`, ลำดับ `<h1>`→`<h2>` ที่ถูกต้อง, `alt` ครบทุกภาพ = ทั้ง accessibility และ AI SEO ในงานเดียว

### 4.9 OG / Twitter Card

ค้างมาจากรายงานเดือน ก.ค. — แชร์ลิงก์ใน LinkedIn/LINE ตอนนี้ยังขึ้นเป็นกล่องเปล่า ทั้งที่ช่องทางนี้คือช่องที่ recruiter เห็นเยอะที่สุด

## 6. แผนดำเนินงาน 4 เฟส

### เฟส 0 — หยุดเลือดก่อน (~30 นาที)
| งาน | เวลา |
|---|---|
| แก้เมนูมือถือ ด้วย **delegated event** `$(document).on("click", ".sidebar-toggle", ...)` | 5 นาที |
| ลบ `å` ท้าย `brithday.js` | 1 นาที |
| ใส่ OG / Twitter meta | 10 นาที |
| ตัดที่อยู่เหลือระดับจังหวัด + ตัดเกรดเฉลี่ยออก | 15 นาที |

> **ทำไมต้องเป็น delegated event ไม่ใช่ย้ายเข้า `componentsLoaded`:** เฟส 1 จะเลิกใช้ `fetch` ทำให้ event `componentsLoaded` เปลี่ยนที่มา ถ้าเฟส 0 ย้ายเข้าไปผูกกับ event นั้น เฟส 1 จะทำให้เมนูพังซ้ำอีกรอบ ส่วน delegated event ผูกกับ `document` จึงรอดทั้งสองสถาปัตยกรรม

### เฟส 1 — สถาปัตยกรรม (~1 วัน) ← **ปลดล็อกทุกอย่างที่เหลือ**
| งาน | เวลา |
|---|---|
| เขียน `build.js` ต่อ component → `index.html` static | 3–4 ชม. |
| **เก็บบล็อก init ของ `app.js` ไว้ แล้ว dispatch `componentsLoaded` ตอน `DOMContentLoaded` แทน** | 15 นาที |
| ตรวจว่า jQuery/GSAP/WOW/Isotope ยังทำงานถูกหลังเลิกใช้ fetch | 2 ชม. |
| ตรวจซ้ำด้วย `curl` — ต้องเห็นเนื้อหาครบใน HTML ดิบ | 30 นาที |

## 8. เรื่องที่ต้องขอคำยืนยันก่อนลงมือ

1. **โดเมนจริง** — เจอ remote เป็น `github.com/darkneed02/darkneed02.github.io` จึงตั้งสมมติฐานว่าเว็บอยู่ที่ `https://darkneed02.github.io/` ถ้ามีโดเมนของตัวเอง ต้องรู้ก่อนเพื่อใส่ `canonical`, `og:url`, `sitemap.xml`, JSON-LD `@id` ให้ถูก
2. **ตำแหน่งงานเป้าหมาย** — จะเล็ง "Full Stack Developer", "Backend Developer (Golang)", "Software Engineer" หรืออื่น? อันนี้กำหนดคำใน `<title>`, `<h1>`, `jobTitle` และ `llms.txt` ทั้งหมด
3. **ตลาดเป้าหมาย** — บริษัทไทยเป็นหลัก หรือรวม remote ต่างประเทศด้วย? ถ้ารวมต่างประเทศ ความสำคัญของหน้า `/en/` จะขึ้นมาเท่ากับหน้าไทย
4. **ตัวเลขผลงาน** — มีตัวเลขผลลัพธ์จริงจากงานที่ผ่านมาไหม (ลดเวลาเท่าไหร่ ผู้ใช้กี่คน ทรานแซคชันต่อวันเท่าไหร่) ตัวนี้เพิ่มโอกาสถูก AI อ้างอิงมากที่สุดในบรรดางานทั้งหมด
