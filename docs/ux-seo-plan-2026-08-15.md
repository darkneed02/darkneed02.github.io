## 0. บทสรุปผู้บริหาร

ตรวจแล้วพบว่า **ปัญหาหลักไม่ใช่เรื่องดีไซน์ แต่เป็นเรื่องสถาปัตยกรรมการเรนเดอร์**

หลักฐานที่วัดได้จริง (เสิร์ฟไฟล์จริงแล้ว `curl` ดู HTML ดิบ):

```
bytes ที่ส่งกลับ:              6,824
คำที่มองเห็นได้ใน <body>:      0
"จารุวัฒน์" ใน body:           0 ครั้ง (มีแค่ใน <title> กับ meta)
```

**เนื้อหาทั้งหน้าเป็นศูนย์สำหรับทุก crawler ที่ไม่รัน JavaScript** เพราะ `assets/js/app.js` โหลดทุก section ด้วย `fetch().innerHTML`

เรื่องนี้สำคัญมากกับโจทย์ที่ตั้งไว้ เพราะ:

| ตัวอ่าน | รัน JS ไหม | เห็นอะไร |
|---|---|---|
| Googlebot | รัน (แต่ delay เป็นวัน) | เห็นครบ — ช้า |
| GPTBot / OAI-SearchBot (ChatGPT) | **ไม่รัน** | หน้าเปล่า |
| ClaudeBot (Claude) | **ไม่รัน** | หน้าเปล่า |
| PerplexityBot | **ไม่รัน** | หน้าเปล่า |
| ATS / บอทดูดโปรไฟล์ของ HR | **ไม่รัน** | หน้าเปล่า |
| LINE / Facebook / LinkedIn preview | **ไม่รัน** | ไม่มีรูป ไม่มีคำอธิบาย |

> **ข้อสรุป: ต่อให้ออกแบบ UI ใหม่สวยแค่ไหน ถ้ายังฉีดเนื้อหาด้วย JS อยู่ โจทย์ "ให้ AI มาหาตำแหน่งเจอ" จะทำไม่ได้เลย**
> ดังนั้นงานข้อ 1 (สถาปัตยกรรม) ต้องมาก่อนงานดีไซน์ทั้งหมด

## 1. ทางเลือกที่ 1 — สถาปัตยกรรมการเรนเดอร์ (ต้องเลือกก่อน)

### แนวทาง A — รวมเป็น `index.html` ไฟล์เดียวแบบ static

เอาเนื้อหาจาก component ทั้ง 13 ไฟล์มาแปะใน `index.html` ตรงๆ ครั้งเดียวจบ

| ข้อดี | ข้อเสีย |
|---|---|
| ไม่ต้องมี build tool อะไรเลย | ไฟล์เดียว ~1,400 บรรทัด แก้ยากขึ้น |
| crawler เห็นครบทันที 100% | เสียการแยก component ที่ทำไว้ดีแล้ว |
| เร็วที่สุด — ยิงไฟล์เดียว ไม่มี 13 request | |
| GitHub Pages รองรับตรงๆ | |

### แนวทาง B — build step เล็กๆ ⭐ **แนะนำ**

เขียนสคริปต์สั้นๆ (Node หรือ shell ~40 บรรทัด) ที่เอา `component/**` มาต่อกันเป็น `index.html` ตอน build

```
component/  ──(build.js)──►  index.html   (static, commit ลง repo)
     ▲                            │
   แก้ตรงนี้                 GitHub Pages เสิร์ฟตัวนี้
```

| ข้อดี | ข้อเสีย |
|---|---|
| ยังแก้เป็น component เหมือนเดิม | ต้องจำว่าแก้แล้วต้อง build |
| output เป็น static 100% — crawler เห็นครบ | เพิ่มไฟล์ build script 1 ไฟล์ |
| ทำ 2 ภาษา (TH/EN) จาก source เดียวได้ | |
| ใส่ GitHub Action ให้ build อัตโนมัติตอน push ได้ | |

**หมายเหตุสำคัญ:** repo นี้คือ `darkneed02.github.io` = GitHub Pages
GitHub Pages **ไม่ build ให้** ดังนั้น `index.html` ที่ build แล้วต้อง commit ลง repo
(หรือใช้ GitHub Action build ให้ตอน push — แนะนำทำในเฟส 2)

และ `docker-compose.yml` mount root แบบ `:ro` ดังนั้น output ต้องออกที่ root ของ repo เท่านั้น

### แนวทาง C — ย้ายไป SSR framework (Astro / Next.js) ❌ **ไม่แนะนำ**

ตอบโจทย์ SEO ได้ดีที่สุดในทางทฤษฎี แต่:
- ขัดกับที่กำหนดไว้ว่า **"ใช้ css js ของธีมที่มีอยู่"**
- ธีมนี้พึ่ง jQuery + GSAP + WOW + Isotope + Swiper ซึ่งพังง่ายมากบน React lifecycle
- งานที่ควรใช้ 2 สัปดาห์ จะกลายเป็น 2 เดือน

**→ เลือก B**

## 2. ทางเลือกที่ 2 — สองภาษากับ SEO

ตอนนี้ EN มีอยู่แค่ใน `i18n.js` (สลับด้วย JS) แปลว่า **เวอร์ชันอังกฤษไม่มีตัวตนใน Google เลย** และไม่มี `hreflang`

สำคัญมาก เพราะ recruiter ต่างชาติ / บริษัท international / AI ที่ค้นเป็นภาษาอังกฤษ จะหาไม่เจอ

| ทางเลือก | ผลลัพธ์ |
|---|---|
| **B1 — สองหน้า static: `/` (ไทย) + `/en/` (อังกฤษ)** ⭐ | ทั้งสองภาษาถูก index จริง, ใส่ `hreflang` + `canonical` ไขว้กันได้, AI ค้นภาษาอังกฤษเจอ |
| B2 — ไทยอย่างเดียวเป็นหลัก EN เป็นแค่ปุ่มสลับ | ทำง่ายกว่า แต่เสียตลาด recruiter ต่างชาติทั้งหมด |

**→ แนะนำ B1** — ถ้าเลือกแนวทาง B (build step) ตัวสคริปต์สร้างสองหน้านี้จาก source เดียวกันได้เลย ไม่ต้องเขียนเนื้อหาซ้ำ

## 4. งาน SEO เฉพาะทางสำหรับ HR และ AI

ตอนนี้ **ไม่มีไฟล์เหล่านี้เลยสักไฟล์**: `robots.txt`, `sitemap.xml`, `llms.txt`, `resume.json`, OG tags, JSON-LD

### 4.1 ให้ AI crawler เข้าถึงได้ — `robots.txt`

ระบุอนุญาต bot ที่เกี่ยวกับการหางานให้ชัด: `GPTBot`, `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`, `PerplexityBot`, `Google-Extended`, `Bingbot` + บรรทัด `Sitemap:`

ถ้าบล็อกบอทพวกนี้ = แพลตฟอร์มนั้นอ้างอิงเราไม่ได้เลย

### 4.2 JSON-LD — `ProfilePage` ครอบ `Person`

ตัวนี้คือหัวใจของ "ให้ AI รู้ว่าเราคือใครและหางานตำแหน่งอะไร"

| field | ใส่อะไร |
|---|---|
| `name` / `alternateName` | จารุวัฒน์ อำนวยสัตย์ / Jaruwat Amnuaysat |
| `jobTitle` | Full Stack Developer, Programmer |
| `knowsAbout` | Golang, PHP, Vue.js, PostgreSQL, REST API, Docker, Automation |
| `hasOccupation` → `Occupation` | ชื่อตำแหน่งที่ต้องการ + `occupationLocation` |
| `worksFor` / `alumniOf` | บริษัทและสถาบัน (มีข้อมูลครบใน experience แล้ว) |
| `sameAs` | LinkedIn, GitHub, Facebook |
| `address` | **ระดับจังหวัดเท่านั้น** — "ปทุมธานี, ประเทศไทย" |
| `email` | อีเมลติดต่อ |

*(`Person.seeks` → `Demand` มีใน schema.org จริง แต่แทบไม่มีตัวไหนอ่าน — ใส่ได้แต่ไม่ต้องพึ่ง)*

### 4.3 `llms.txt` — สรุป CV แบบ markdown ล้วน

ไฟล์ text ที่ AI อ่านง่ายที่สุด วางที่ root: ชื่อ, ตำแหน่งที่หา, stack, สรุปประสบการณ์แต่ละที่, ช่องทางติดต่อ

### 4.4 `resume.json` — มาตรฐาน JSON Resume

มาตรฐานจริงที่เครื่องมือ AI matching / ATS หลายตัว parse ได้ตรงๆ ต้นทุนต่ำ ผลตอบแทนสูงสำหรับโจทย์นี้โดยเฉพาะ

### 4.5 คำในหัวเรื่องต้องตรงกับที่คนค้นจริง

ตอนนี้ `<title>` คือ *"จารุวัฒน์ อำนวยสัตย์ — Programmer & Developer"* — ค้นด้วยชื่อถึงจะเจอ แต่ **ไม่มีใครค้นชื่อคนที่ยังไม่รู้จัก**

ต้องมีคำที่ HR/AI ค้นจริง: ตำแหน่ง + stack + จังหวัด
เช่น `"Full Stack Developer (Golang/PHP/Vue) ปทุมธานี — จารุวัฒน์ อำนวยสัตย์"`

### 4.6 บล็อก FAQ + `FAQPage` schema

AI ดึงคำตอบเป็น "ท่อน" ไม่ใช่ทั้งหน้า — เขียนคำถามที่ HR ถามจริง คำตอบละ 40–60 คำ จบในตัว:
- "รับงานประเภทไหน / พร้อมเริ่มงานเมื่อไหร่"
- "ถนัด tech stack อะไรบ้าง"
- "ทำงาน remote / onsite ที่ไหนได้"
- "มีประสบการณ์กี่ปี ทำอะไรมาบ้าง"

### 4.7 เขียนผลงานเป็น "ตัวเลข"

งานวิจัย GEO (Princeton, KDD 2024) วัดผลกับ AI search engine พบว่า **การใส่สถิติ/ตัวเลขเพิ่มโอกาสถูกอ้างอิง ~37–40%** ส่วน **keyword stuffing ลดลง 10%**

แปลว่า: `"ลดเวลาประมวลผลรายงานจาก 4 ชม. เหลือ 12 นาที"` ทรงพลังกว่า `"พัฒนาระบบรายงาน"` มาก

### 4.8 Semantic HTML — เพราะ AI agent อ่าน accessibility tree

AI agent รุ่นใหม่อ่านหน้าเว็บผ่าน accessibility tree เดียวกับที่ screen reader ใช้
ดังนั้น `<main>`, `<article>`, `<section>`, ลำดับ `<h1>`→`<h2>` ที่ถูกต้อง, `alt` ครบทุกภาพ = ทั้ง accessibility และ AI SEO ในงานเดียว

### 4.9 OG / Twitter Card

ค้างมาจากรายงานเดือน ก.ค. — แชร์ลิงก์ใน LinkedIn/LINE ตอนนี้ยังขึ้นเป็นกล่องเปล่า ทั้งที่ช่องทางนี้คือช่องที่ recruiter เห็นเยอะที่สุด

## 6. แผนดำเนินงาน 4 เฟส

### เฟส 0 — หยุดเลือดก่อน (~30 นาที)
| งาน | เวลา |
|---|---|
| แก้เมนูมือถือ ด้วย **delegated event** `$(document).on("click", ".sidebar-toggle", ...)` | 5 นาที |
| ลบ `å` ท้าย `brithday.js` | 1 นาที |
| ใส่ OG / Twitter meta | 10 นาที |
| ตัดที่อยู่เหลือระดับจังหวัด + ตัดเกรดเฉลี่ยออก | 15 นาที |

> **ทำไมต้องเป็น delegated event ไม่ใช่ย้ายเข้า `componentsLoaded`:** เฟส 1 จะเลิกใช้ `fetch` ทำให้ event `componentsLoaded` เปลี่ยนที่มา ถ้าเฟส 0 ย้ายเข้าไปผูกกับ event นั้น เฟส 1 จะทำให้เมนูพังซ้ำอีกรอบ ส่วน delegated event ผูกกับ `document` จึงรอดทั้งสองสถาปัตยกรรม

### เฟส 1 — สถาปัตยกรรม (~1 วัน) ← **ปลดล็อกทุกอย่างที่เหลือ**
| งาน | เวลา |
|---|---|
| เขียน `build.js` ต่อ component → `index.html` static | 3–4 ชม. |
| **เก็บบล็อก init ของ `app.js` ไว้ แล้ว dispatch `componentsLoaded` ตอน `DOMContentLoaded` แทน** | 15 นาที |
| ตรวจว่า jQuery/GSAP/WOW/Isotope ยังทำงานถูกหลังเลิกใช้ fetch | 2 ชม. |
| ตรวจซ้ำด้วย `curl` — ต้องเห็นเนื้อหาครบใน HTML ดิบ | 30 นาที |

## 12. บันทึกผลเฟส 2 — SEO / AEO (15 ส.ค. 2569)

### 12.1 แหล่งข้อมูลใหม่: `data/profile.js`

ปัญหาที่ต้องกันไว้ก่อนคือ **ข้อมูลชุดเดียวกันต้องไปโผล่ 4 ที่** (JSON-LD, llms.txt, resume.json, หน้าเว็บ)
ถ้าเขียนแยกกันจะหลุดจากกันแน่นอน จึงรวมประวัติงาน/การศึกษา/ใบรับรอง/ทักษะไว้ที่ `data/profile.js`
แล้วให้ `build.js` generate ทุกไฟล์จากตรงนั้น — แก้ที่เดียว ตรงกันทุกที่

### 12.2 ไฟล์ที่ generate เพิ่ม

| ไฟล์ | ขนาด | ทำอะไร |
|---|---|---|
| `robots.txt` | 974 B | อนุญาต 18 bot ที่เกี่ยวกับ AI/หางาน แบบระบุชื่อ + ชี้ `Sitemap:` |
| `sitemap.xml` | 876 B | 2 URL พร้อม `xhtml:link` hreflang ไขว้กัน (ไม่ใส่ `lastmod` เพราะจะทำให้ build ไม่ deterministic) |
| `llms.txt` | 6.8 KB | สรุปโปรไฟล์แบบ markdown — อังกฤษเป็นหลัก มีสรุปภาษาไทยท้ายไฟล์ |
| `resume.json` | 6.4 KB | มาตรฐาน JSON Resume (อังกฤษ) |
| `resume.th.json` | 8.7 KB | JSON Resume ฉบับไทย |

### 12.3 JSON-LD

ทั้งสองหน้าได้ 2 บล็อก ตรวจ parse ผ่านแล้ว:

1. **`ProfilePage` → `mainEntity: Person`** — `name`, `alternateName`, `jobTitle` (3 ตำแหน่ง),
   `knowsAbout` (22 รายการ), `hasOccupation` → `Occupation` พร้อม `occupationLocation` (ปทุมธานี + กรุงเทพฯ),
   `worksFor`, `alumniOf`, `sameAs`, `hasCredential` **8 ใบรับรองพร้อมลิงก์ตรวจสอบ**,
   `address` ระดับจังหวัดเท่านั้น
2. **`FAQPage`** — 5 คำถาม ดึงข้อความจาก `i18n.js` ตัวเดียวกับที่แสดงบนหน้า **จึงหลุดจากกันไม่ได้**

### 12.4 FAQ

section ใหม่ `component/body/faq.html` วางไว้ก่อน "ติดต่อ" (ช่วยลดช่องว่างของข้อ 5.7 ไปในตัว)
5 คำถามที่ HR ถามจริง คำตอบละ ~40–60 คำ จบในตัว เพราะ AI ดึงคำตอบเป็น "ท่อน" ไม่ใช่ทั้งหน้า
เพิ่มเมนู "คำถามที่พบบ่อย" ในแถบนำทางด้วย

### 12.5 ระบบแปล attribute (`data-i18n-attr`)

ของเดิมแปลได้แค่เนื้อหา ทำให้หน้า EN มี `alt="จารุวัฒน์ อำนวยสัตย์"` ค้างอยู่
เพิ่ม `data-i18n-attr="alt:key;title:key"` ใน `build.js` — ตอนนี้หน้า EN **ไม่มีข้อความไทยค้างใน attribute แล้ว**

### 12.6 GitHub Action

`.github/workflows/build.yml` — push แก้ `component/**`, `data/**`, `i18n.js`, `build.js` เข้า `main`
แล้ว build + commit ผลลัพธ์กลับให้อัตโนมัติ ไม่วนลูปเพราะ trigger ดูเฉพาะไฟล์ source
ถ้าคำแปลหาย `build.js` exit 1 → workflow แดง

> **ต้องเช็คก่อนใช้:** ถ้า GitHub Pages ตั้ง deploy จาก branch อื่นที่ไม่ใช่ `main` ต้องแก้ `branches:` ให้ตรง

## 14. รอบประเมินและแก้ UI/UX (16 ส.ค. 2569)

### 14.1 CTA หลักหายไปจาก Hero (ปัญหาใหญ่ที่สุด)

แผนข้อ 3 ระบุไว้ว่า Hero ต้องมีปุ่ม `[ดาวน์โหลด Resume] [ติดต่อ]` แต่ของจริงมีแค่
ไอคอน 40px ปนอยู่ในแถวโซเชียล — คนที่เปิดมา 30 วินาทีจึงไม่มีปุ่มให้กด

เพิ่ม `.rs-banner-actions` (ปุ่มคู่ ขนาด 48px) **โดยไม่ใส่ class `wow`**
เพราะ CTA หลักต้องมองเห็นแน่นอนไม่ว่าอนิเมชันจะทำงานหรือไม่

พร้อมกันนั้นสร้างชุดปุ่มกลาง `.rs-btn` / `.rs-btn-primary` / `.rs-btn-ghost` / `.rs-btn-outline`
เดิมสไตล์ปุ่มผูกกับ `.rs-about-actions .btn` เท่านั้น ปุ่ม CTA ในส่วน "ติดต่อ" จึงหลุดสไตล์
กลายเป็นลิงก์เล็กๆ กลางกล่องเปล่า ตอนนี้ทั้ง hero / about / contact ใช้ชุดเดียวกัน

### 14.2 section ใบรับรอง — เขียนใหม่ทั้ง section

ของเดิมยืมสไตล์ section ประสบการณ์ผ่าน selector `[style*="padding: 12px"]` ผลคือ
หัวหมวดเป็นแถบกรมท่าเต็มความกว้างที่มีตัวหนังสือ `rgba(255,255,255,.50)` 12px อ่านไม่ออก
และการ์ดกว้างครึ่งคอลัมน์ หมวดที่มีใบเดียวจึงเหลือพื้นที่ว่างครึ่งจอ

เขียนใหม่เป็น `.rs-cert-*` ของตัวเอง: หัวหมวดเป็นบรรทัดเดียวมีเส้นคั่น
การ์ดเป็นกริด `auto-fill minmax(320px, 1fr)` + `align-items: start` และลบ selector hack ทิ้ง

### 14.3 ตัดแถบเปอร์เซ็นต์ทักษะออก

`PHP 90%` / `Laravel 85%` เป็นการให้คะแนนตัวเองที่ยืนยันไม่ได้ ไม่มีเกณฑ์กลางว่า
90% ต่างจาก 85% อย่างไร และเป็นจุดที่ผู้สัมภาษณ์สายเทคนิคมองว่าลดความน่าเชื่อถือ
ระดับความชำนาญสื่อผ่านการจัดกลุ่ม Primary / Strong / กำลังศึกษา ที่มีอยู่แล้ว
ตัดออก 11 บล็อก การ์ดเตี้ยลงจนจัดสองคอลัมน์ได้ ส่วนนี้สั้นลงและสแกนเร็วขึ้น

### 14.4 ช่องว่างตายจากการบังคับความสูงเท่ากัน

| จุด | เดิม | แก้เป็น |
|---|---|---|
| การ์ดประสบการณ์ | `height: 100%` — การ์ดฝึกงานที่เนื้อหาน้อยยืดตามการ์ดที่ยาวที่สุด | `height: auto` |
| กลุ่มทักษะ | `height: 100%` — กลุ่ม Primary เหลือพื้นที่ว่างท้ายการ์ด ~110px | `height: auto` |
| การ์ด case study | `align-items: center` — ภาพแผนภาพลอยกลางการ์ด มีช่องว่างบน-ล่างข้างละเกือบ 100px | `align-items: start` |

### 14.5 รูปถ่ายซ้ำและตีกับธีม

รูปชุดครุยพื้นหลังฟ้าสตูดิโอถูกใช้ 2 จุด (hero + เกี่ยวกับ) และสีตีกับโทนกรมท่าของเว็บ

- ถอดรูปออกจาก section "เกี่ยวกับ" — เห็นรูปเดิมซ้ำในหน้าเดียวไม่ได้เพิ่มข้อมูล
  และเบียดพื้นที่เนื้อหาที่ HR ต้องอ่านจริง
- รูปใน hero: **ลองปรับสีแล้วถอยกลับ** ครั้งแรกใช้ `saturate(.32)` + ซ้อนกรมท่าโหมด `multiply`
  เพื่อให้พื้นหลังฟ้าสตูดิโอกลืนกับ hero แต่ผลจริงคือทั้งรูปกลายเป็นโทนเทา ใบหน้าหม่นไปด้วย
  (เจ้าตัวทักว่า "ภาพมันเทา") **ตอนนี้รูปเป็นสีธรรมชาติ 100% ไม่แตะสีในรูปเลย**
  ใช้กรอบ + เงา + ไล่เฉดบางๆ ที่ขอบล่าง (สูง 22%, `rgba(15,26,48,.38)`) เชื่อมรูปเข้ากับพื้นแทน

  > บทเรียน: การลดความอิ่มสีทั้งรูปเพื่อแก้ปัญหาพื้นหลัง กระทบสีผิวคนในรูปเสมอ
  > ถ้าจะให้พื้นหลังกลืนกับธีมจริงๆ ต้องแยกพื้นหลังออกจากตัวคน (ลบพื้นหลัง) ที่ตัวไฟล์ภาพ
  > ไม่ใช่ที่ CSS

พร้อมกันนี้แก้หัวข้อ `about.title` ที่ทักทาย + บอกชื่อซ้ำกับ hero
เปลี่ยนเป็นประโยคที่บอกจุดขาย ("ถนัดระบบหลังบ้านองค์กรที่ต้องเชื่อมหลายระบบเข้าด้วยกัน")

### 14.6 Accessibility

| เรื่อง | เดิม | แก้เป็น |
|---|---|---|
| Focus ring | `outline: none` โดยมีแค่เส้นขอบ 1px แทน | `:focus-visible` วง 3px ทั้งหน้า + สีอ่อนบนพื้นกรมท่า |
| ปุ่มที่มีแต่ไอคอน | ไม่มีชื่อให้ screen reader (โซเชียล footer, แฮมเบอร์เกอร์, ปิด offcanvas) | `aria-label` + `data-i18n-attr` แปลตามภาษา |
| ปุ่มขึ้นบนสุด | เป็น `<div>` — tab ไปไม่ถึง กด Enter ไม่ได้ | `<button>` (ตัวจัดการคลิกเดิมใน `main.js` ยังทำงาน — ทดสอบด้วยคีย์บอร์ดแล้ว) |
| ปุ่มเมนูมือถือของ meanmenu | ปลั๊กอินสร้าง `<a class="meanmenu-reveal">` ที่ไม่มีข้อความ | เติม `aria-label` ใน `app.js` หลัง init |
| `prefers-reduced-motion` | ไม่มีเลย — วงโคจร จุดกะพริบ marquee วิ่งไม่หยุด | ปิดอนิเมชันทั้งหมด + บังคับให้ element ของ WOW แสดงเสมอ |
| คอนทราสต์ | ดูตาราง 14.6.1 | วัดใหม่ทุกจุดจนผ่าน AA |

#### 14.6.1 คอนทราสต์ — วัดจริง ไม่ได้ประเมินด้วยตา

วัดโดยอ่านสีตัวอักษรจาก `getComputedStyle` แล้วผสมทับสีพื้นที่ไล่หาจากบรรพบุรุษใน DOM
(รวมชั้นโปร่งใสทุกชั้น) ไม่ใช่การเทียบค่าที่เขียนไว้ใน CSS

| จุด | เดิม | หลังแก้ |
|---|---|---|
| `--cv-text-light` บนพื้นขาว | #94A3B8 = **2.6:1** | #5E6B7F = **5.4:1** |
| `--cv-text-muted` บนพื้น `--cv-bg` / `--cv-border-light` (ชิป, หัวหมวดใบรับรอง, chip เทคโนโลยี) | #64748B = **4.26:1** — ผ่านบนพื้นขาวแต่ตกบนพื้นเทาอ่อน | #5A6880 = **5.1:1** |
| `.rs-contact-list-content span` | `rgba(255,255,255,.40)` = **3.46:1** | `.62` = **6.72:1** |
| `.rs-footer-copyright p` | `rgba(255,255,255,.40)` = **3.02:1** | `.62` = **6.86:1** |
| `.offcanvas-title-meta` | `rgba(255,255,255,.40)` = **3.78:1** | `.62` = **7.27:1** |

ตรวจซ้ำ 12 จุดที่เสี่ยงที่สุด: **ผ่าน AA ครบทุกจุด** (ต่ำสุด 4.89:1)

> **บทเรียนเรื่องวิธีวัด:** ครั้งแรกลองวัดด้วยการถ่ายพิกเซลจริง (ซ่อนตัวอักษร → ถ่ายกรอบเดิม → ได้สีพื้น)
> ซึ่งควรแม่นกว่าเพราะครอบคลุม gradient ด้วย แต่ได้ค่าเพี้ยน เช่น 1.05:1 บน hero
> สาเหตุมีสองชั้น: (1) `scroll-behavior: smooth` ทำให้อ่าน `getBoundingClientRect`
> กลางอนิเมชัน กรอบที่ clip จึงไปตกคนละที่ (2) ตอนบังคับให้ offcanvas แสดงเพื่อวัด
> มันเป็นแผงเต็มจอที่บังทั้งหน้า ค่าที่วัดหลังจากนั้นจึงเป็นพื้นหลังของ offcanvas ทั้งหมด
> **ตัวเลขที่ใช้ในตารางข้างบนมาจากวิธี DOM-walk ซึ่งเชื่อถือได้กับ section ที่พื้นหลังเป็นสีทึบ**
> ส่วน hero/marquee ที่พื้นหลังเป็น gradient คำนวณแยกมือ — ทั้งสองจุดผ่านสบาย (5.6:1 และ 8.0:1)

### 14.7 ความยาวบรรทัดและน้ำหนักตัวอักษร

ที่ 1440px เนื้อความใน FAQ และ case study ยาวเกิน 110 ตัวอักษรต่อบรรทัด
ใส่เพดาน 72–76ch และเลิกใช้ `font-weight: 300` กับเนื้อความที่ต้องอ่านจริง (เปลี่ยนเป็น 400)

### 14.8 เรื่องที่ต้องให้เจ้าตัวยืนยัน

**หัวข้อ section "เกี่ยวกับ" ถูกเขียนคำใหม่** — เดิมเป็น "สวัสดีครับ ผม จารุวัฒน์ อำนวยสัตย์"
ซึ่งทักทายและบอกชื่อซ้ำกับ hero ที่อยู่เหนือขึ้นไป การตัดคำซ้ำเป็นเรื่อง UX
แต่ **คำที่เขียนแทนเป็นถ้อยคำวางตำแหน่งตัวเอง ซึ่งข้อ 10 เคยตกลงกับเจ้าตัวไว้แล้ว**
จึงควรอ่านทวนและยืนยัน:

| | ไทย | อังกฤษ |
|---|---|---|
| ใหม่ | ถนัดระบบหลังบ้านองค์กร<br>**ที่ต้องเชื่อมหลายระบบเข้าด้วยกัน** | Enterprise back-office systems<br>**that have to talk to each other** |

สอดคล้องกับจุดขายที่สรุปไว้ในข้อ 10 (ระบบหลังบ้าน + SAP + เข้ารหัสไฟล์ธนาคาร + Automation)
ถ้าอยากใช้คำอื่น แก้ที่ `about.title` ใน `assets/js/i18n.js` ทั้งสองภาษาแล้ว `node build.js`

### 14.9 เรื่องที่ตรวจแล้วแต่ตั้งใจไม่แก้

- **อายุ / เพศ ใน section เกี่ยวกับ** — เป็นธรรมเนียมของใบสมัครงานไทยและหน้าไทยเป็นหน้าหลัก
  การตัดออกเป็นการตัดสินใจเรื่องการวางตำแหน่ง ไม่ใช่การแก้ UX จึงยกให้เจ้าตัวตัดสิน
  (ต่างจากเกรดเฉลี่ย/ที่อยู่เต็มที่ตัดไปแล้วในเฟส 0)
- **`โปรเจกต์ 20+`** — ยังยืนยันไม่ได้ (ข้อ 13.7) แต่จะแทนด้วยตัวเลขที่คำนวณเองก็ไม่ถูกต้องเช่นกัน
  ทางเลือกคือคงไว้ หรือเปลี่ยนเป็นตัวเลขที่หน้าเว็บพิสูจน์ได้แล้ว เช่น "8 ใบรับรอง"
- **ประวัติการศึกษาระดับมัธยม** — คงไว้ตามธรรมเนียมเรซูเม่ไทย

### 14.10 คลาสที่ชนกับธีม (เจอตอนตรวจรอบสอง)

ตั้งชื่อคลาสปุ่มว่า `.rs-btn` / `.rs-banner-actions` ซึ่ง **ชนกับคลาสที่ธีมมีอยู่แล้ว**
(`main.css:1319` และ `main.css:6759`) ตัวหลังเป็น `.rs-banner-one .rs-banner-actions .rs-btn`
specificity สูงกว่าที่เขียนใน `custome.css` จึงบังคับ `height: 56px` เฉพาะปุ่มใน hero
ผลคือปุ่ม hero สูงไม่เท่าปุ่มใน about/contact โดยไม่มีใครสังเกต

เปลี่ยนชื่อเป็น `.cv-btn*` / `.cv-hero-actions` — ใช้ prefix `cv-` เหมือน token `--cv-*`
ที่ repo นี้ใช้อยู่แล้ว ตอนนี้ปุ่มทั้งสามที่สูง 53px เท่ากันหมด

> **กฎที่ควรถือต่อไป: คลาสใหม่ทุกตัวใน `custome.css` ใช้ prefix `cv-`**
> prefix `rs-` เป็นของธีม การเอามาใช้ซ้ำจะโดน override เงียบๆ เมื่อไหร่ก็ได้

เรื่องเดียวกันยังทำให้เจออีกจุด: ชิปใน hero มี `::before` เป็น glyph ของ remixicon (`\eb79`)
ที่ธีมใส่ไว้ ตำแหน่ง `inset-inline-start: 0` ไปตกบนมุมโค้งของแคปซูล เห็นเป็นเศษเส้นจางๆ
ที่ขอบซ้ายทุกชิป — ปิดด้วย selector ที่ specificity เท่ากับธีม

### 14.11 ผลตรวจ

`node build.js` ผ่าน ไม่มีคำเตือนคำแปลตกค้าง
ทดสอบ 2 ภาษา × 3 ขนาด (390 / 768 / 1440): ไม่มี JS error, ไม่มี horizontal scroll,
ไม่มีข้อความไทยค้างในหน้า EN, WOW เผยเนื้อหาครบทุก element, ปุ่มที่กด tab ถึงมีชื่อครบทุกตัว,
ปุ่มขึ้นบนสุดใช้คีย์บอร์ดได้จริง

ความสูงหน้าเดสก์ท็อป 11,842px → 11,469px (แน่นขึ้นโดยไม่ได้ตัดเนื้อหาออกนอกจากแถบเปอร์เซ็นต์)

ตรวจเพิ่มอีกสามชุดที่ชุดแรกครอบไม่ถึง:

1. **`prefers-reduced-motion`** — เปิดโหมดนี้แล้วโหลดหน้า **โดยไม่ scroll เลย**
   element ที่มี class `wow` ทั้ง 48 ตัวมองเห็นครบ (0 ตัวยังซ่อน) ข้อความ 10,147 ตัวอักษร
   สำคัญเพราะบล็อกนี้ใช้ `!important` สู้กับ inline style ของ WOW ถ้าแพ้ ผู้ใช้ที่เปิด
   Reduce Motion (ค่าที่คนเปิดกันมากบน iOS/macOS) จะเห็นหน้าเว็บที่มีช่องว่างเปล่าเป็นก้อนๆ
2. **ข้อความไทยค้างใน attribute ของหน้า EN** — `aria-label` ที่เพิ่มใหม่วิ่งผ่าน `applyDictAttr`
   ซึ่งเป็นคนละเส้นทางกับ `applyDict` การตรวจ `textContent` อย่างเดียวจึงจับไม่ได้
   ผลตรวจ: label ใหม่ทุกตัวเป็นอังกฤษถูกต้อง (`Open menu` / `Close menu` / `Back to top`)
   เหลือข้อความไทยสองจุดที่ **ตั้งใจให้เป็นไทย**: `<link title="JSON Resume (ไทย)">`
   (อธิบายไฟล์ภาษาไทย) และ `aria-label="เปลี่ยนเป็นภาษาไทย"` บนปุ่มสลับภาษา
   (ธรรมเนียมคือเขียนป้ายปุ่มสลับภาษาด้วยภาษาปลายทาง)
3. **คอนทราสต์** — ดูตาราง 14.6.1

> หมายเหตุเรื่อง `data-i18n-attr`: README เขียนว่าใช้ได้เฉพาะ tag ที่ไม่มีเนื้อหาจาก dict
> (`img`, `a`, `input` ฯลฯ) แต่โค้ดจริงใน `build.js` ตรวจแค่ว่า element เดียวกันต้องไม่มี
> ทั้ง `data-i18n` และ `data-i18n-attr` พร้อมกัน การใส่บน `<button>` (ปุ่มปิด offcanvas)
> จึงทำงานได้ — ยืนยันด้วยผลตรวจข้อ 2 แล้ว ไม่ใช่แค่ "build ไม่ error"
